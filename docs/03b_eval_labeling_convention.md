> 版本：v1.2（2026-10-22）
> 适用文件：`eval/rag/dataset/eval_set_v1_all.jsonl`（150 条，唯一真源）与 `eval/rag/dataset/eval_set_v1.jsonl`（20 条子集）
> 上游文档：`docs/「比特严选」评估集 Query 模板设计.md`（query 设计）、`knowledge_base/_meta/writing_guide.md`（知识库写作规范）
> 被引用：`docs/eval-series-outline.md` 第 2 篇

---

## 一、为什么需要这份规范

评估集里有三个字段直接决定指标是否可信：

| 字段 | 被谁消费 | 标错的后果 |
|---|---|---|
| `ground_truth` | RAGAS `answer_correctness`、`context_recall`（作为 `reference`） | 写成“应推荐……”这类元指令时，judge 拿模型的真实回答去和一句指令比对，`answer_correctness` 系统性偏低；`context_recall` 拆出的 statement 也不是事实，召回好坏无从判断 |
| `expected_doc_ids`（must） | `hit@K`、`recall@K`、`mrr@10` | 塞进冗余或不可召回的文档，Recall 上限被人为压低，分数下降并不代表检索变差 |
| `expected_doc_ids_nice`（nice） | `recall_inclusive@K` | 缺省时 inclusive 退化为 must；乱塞文档会让 inclusive 失去意义，因为 nice 也进分母（见第五节） |

v1.1 只对 S1-01..S1-05 做了分层，其余样本的 `ground_truth` 大多是元指令。v1.2 按本规范重写了全部 150 条。

---

## 二、字段约定

| 字段 | 类型 | 约定 |
|---|---|---|
| `expected_doc_ids` | `list[str]` | must：支撑 `ground_truth` 核心陈述的**最小充分文档集**。`requires_rag=true` 时不能为空 |
| `expected_doc_ids_nice` | `list[str]` | nice：与问题相关、能支撑次要陈述或与 must 信息重复的扩展文档。可为空，但**字段必须存在** |
| `ground_truth` | `str` | 客服直接回复用户的标准答案，自然语言，不含任何对模型的要求 |

字段顺序统一为：`query_id, query, intent_l1, intent_l2, difficulty, requires_rag, expected_answer_type, expected_doc_ids, expected_doc_ids_nice, trap_type, ground_truth, eval_metrics`。

## 三、ground_truth 写法

### 3.1 五条原则

1. **写答案，不写要求。** ground_truth 是“客服应该对用户说的那段话”，不是“模型应该做什么”。
   - 错：`应命中维修报价说明，给出预估区间并说明以检测报价为准。`
   - 对：`换屏按品类有预估价，实际金额以检测后的维修报价为准：手机 399-1499 元，平板 699-1699 元……`
2. **事实只来自 must + nice 文档。** 数字、型号、入口路径、时效原样照抄知识库，不引入知识库以外的参数。唯一的例外是通用安全提示，例如“远离易燃物”“停止使用”，这类内容不需要来源。
3. **先回答，再展开，最后给边界。** 第一句直接回应问题（能/不能、是多少、选哪个），然后给关键事实或步骤，最后写必要的限制、风险或转人工条件。
4. **知识库没有的信息，明确说没有，不编造。** 写法是“资料没有给出 X，所以没法告诉你准确的 Y”，接着给知识库里能确定的事实和影响因素。
5. **长度适中。** 事实类 40-150 字，步骤和政策类 150-400 字，推荐和对比类 200-450 字，上限约 500 字。reference 过长时，RAGAS 会拆出大量 statement，`context_recall` 和 `answer_correctness` 都会被稀释。

### 3.2 禁用表达

以下写法在 v1.2 中全部清除，新增样本也不得出现：

| 类别 | 例子 | 改成 |
|---|---|---|
| 元指令 | `应检索…` `应命中…` `应说明…` `应引导…` `应提醒…` `需提示…` `回答可补充…` | 直接写出要说明的内容 |
| 系统内部用语 | `走工具` `通过库存工具查询` `知识库中` `RAG 补充` | `以商品页/订单页/结算页显示为准` `资料里` `在售型号中` |
| 文档 ID | `参考 NET_GUIDE_002` | 直接写出该文档里的要点 |
| 自我约束 | `不应编造具体百分比` `回答不要混入…` | `资料没有给出…，所以没法告诉你准确的…` |

### 3.3 按场景的写法

| 场景 | 典型样本 | 写法要点 |
|---|---|---|
| 参数事实 | S2-01、S2-02 | 一两句给出数值，可补一条直接相关的边界（如不支持无线充电） |
| 参数缺失 | S2-07、S2-09、S2-10、S6-02 | 说明资料没有该参数，再给已知参数和影响因素，最后给建议 |
| 推荐 / 组合 | S1-*、S3-07、S7-03 | 按预算或场景分档，每档给型号、价格和推荐理由，最后写不建议的情形 |
| 对比 | S3-01、S3-03、S3-09 | 先写相同点，再按维度写差异，最后给“谁适合哪款” |
| 兼容 / 配件 | S6-* | 第一句给能/不能，然后说明原因和正确的购买口径 |
| 操作步骤 | S8-*、S9-*、S10-*、S12-* | 编号步骤，写清前提条件，最后写失败时的检查项 |
| 故障排查 | F1-*、S13-07、S13-08 | 按文档的排查顺序编号，最后写转人工的条件 |
| 政策 | S14-* ~ S17-* | 先给结论，再写条件、例外、入口路径和时效 |
| 动态信息（价格 / 库存 / 优惠 / 订单） | S4-*、S5-* | 说明属于实时信息、以哪个页面为准，再补知识库里的静态规则（参考价、价保、发货时效）。不承诺具体价格或补货日期 |
| 缺上下文 | S5-05 | 追问缺失信息，并说明确认后怎么查 |
| 未发布 / 竞品 | S5-04、S3-08、C2-02、C2-04 | 不预测、不评价竞品，转为介绍知识库内的商品 |
| 非 RAG（`requires_rag=false`） | F2-*、F3-*、C1-*、C2-* | 写一段理想回复：问候、身份说明、记录反馈、安抚并升级、礼貌拒答。不承诺功能上线，不做法律定性，不声称某功能已支持或不支持 |

## 四、must / nice 判定规则

### 4.1 定义

- **must**：删掉其中任意一篇，`ground_truth` 至少有一条**核心陈述**失去依据。
- **nice**：与问题相关，但只支撑**次要陈述**，或者与 must 提供的信息重复。
- **核心陈述**：直接回答用户问题的那部分，包括结论、关键参数、主要步骤和政策条件。**次要陈述**：补充提醒、替代推荐、保养建议、失败后的检查项等。

### 4.2 判定流程

1. 先写好 `ground_truth`，再标文档，顺序不能反。
2. 把 ground_truth 拆成句子，给每句标出处，并标注它是核心还是次要。
3. 用最少的文档覆盖全部核心陈述，这些文档进 must。
4. 支撑次要陈述的文档，以及与 must 重复的相关文档，进 nice。
5. 与 ground_truth 无关的文档两边都不放，即使它和 query 话题相近。

### 4.3 冗余文档只取一篇进 must

两篇文档提供同一条核心事实时，只把更直接的一篇放进 must，另一篇放 nice。例如 S6-07：“T7 / T7S / T7S Plus 通用边刷”在 `PROD_VAC_001` 和 `PROD_VAC_002` 中都有，所以 must 只放 `PROD_VAC_001`。否则检索器只要召回其中一篇，Recall@K 就会被判为 0.5，但答案其实已经有完整依据了。

### 4.4 按意图的默认倾向

| 意图 | must 通常是 | nice 通常是 |
|---|---|---|
| S1 选购推荐、S7 场景推荐 | 选购指南 GUIDE | 指南中提到的商品详情 PROD（指南已含关键参数时） |
| S2 参数咨询 | 商品详情 PROD | 选购指南、使用手册 |
| S3 对比选购 | 被比较的每一款 PROD（各自独占参数，不算冗余） | 选购指南 |
| S4 价格活动 | 价保政策 POLICY_RET_004，问参考价时加 PROD | — |
| S5 库存到货、S16 物流 | 物流政策 POLICY_LOG_* | 涉及的商品详情 |
| S6 配件兼容 | 相关 PROD | 维护手册、故障码文档 |
| S8 操作、S13 保养 | 对应手册 MANUAL | 基础手册、商品详情 |
| S9 配网 | 配网指南 NET_GUIDE / FAQ_NET | 设备手册、门锁 FAQ |
| S10 APP、S12 联动 | APP_GUIDE / AUTO_GUIDE | 相关设备手册 |
| S11 固件 | CODE_FW_001（回退问题为 CODE_FW_002） | 另一篇 CODE_FW |
| S14 ~ S17 售后政策 | 对应 POLICY | 关联政策 |
| F1 故障 | FAQ 或 CODE 中对应的故障条目 | 另一类故障文档、手册 |

这是起点，不是硬规则。以 4.1 的定义为准：商品详情提供了指南里没有的核心事实时，商品详情也进 must。

### 4.5 不允许标注的文档

- `knowledge_base/_meta/` 下的文件（包括 `PRODUCT_MAPPING`）。`upload_docs.py` 会跳过 `_meta/`，这些文件不会被灌进 Ragent，也就永远不可能被召回。v1.1 的 S3-06、S4-02、S4-07 曾标注 `PRODUCT_MAPPING`，v1.2 已移除，参考价改由对应 PROD 文档支撑。
- 不在 `knowledge_base/0*/` 下的任何 ID。
- `requires_rag=false` 的样本：must 和 nice 都为空。

### 4.6 数量上限

must 通常 1-2 篇，不超过 4 篇。nice 不超过 6 篇。数量超限时，往往说明问题过宽，或者 ground_truth 写进了太多次要信息。

## 五、与指标的关系

```text
Recall@K           = |TopK ∩ M| / |M|
Recall inclusive@K = |TopK ∩ (M ∪ N)| / |M ∪ N|
```

- must 要小而准：多标一篇 must，就会无故拉低所有 K 下的 Recall 和 Hit@1 的意义。
- nice 也进分母：inclusive 不是加分项，nice 标得越多，inclusive 越难拿满。只把真正相关的文档放进 nice。
- RAGAS `context_recall` 拆的是 ground_truth 的 statement：ground_truth 里每一句都应该能在 must+nice 文档中找到出处，否则 recall 低的原因是标注，不是检索。

## 六、新增或修改样本时的自检清单

- [ ] ground_truth 第一句直接回答了问题
- [ ] 没有第 3.2 节里的任何禁用表达
- [ ] ground_truth 里的每个数字、型号、路径都能在 must+nice 文档原文中找到
- [ ] 删掉任意一篇 must，都有核心陈述失去依据；冗余文档只留一篇在 must
- [ ] must 与 nice 无重叠，且不含 `_meta/` 文档
- [ ] `requires_rag=false` 时两个列表都为空；`requires_rag=true` 时 must 非空
- [ ] 改的是全量文件 `eval_set_v1_all.jsonl`；子集 `eval_set_v1.jsonl` 由全量按 query_id 重新生成，不单独修改

### 7.2 校验方式

- 结构：150 条全覆盖；文档 ID 均存在于 `knowledge_base/0*/` 下；must/nice 无重叠；`requires_rag` 与标注一致。
- 文本：用正则扫描元指令和内部用语，命中数为 0。
- 事实：抽取每条 ground_truth 中带单位的数字，逐一与 must+nice 文档原文比对。未匹配的 4 处均来自用户提问本身（如“200 元的券”），或是对文档数字的简单加总。

### 7.3 两份 jsonl 的分叉处理

v1.1 时 20 条子集和全量文件有 9 条内容分叉（F1-01、S11-01、S12-01、S15-01、S15-06、S17-01、S4-06、S6-01、S8-01），两份文件修改时间相同，无法判断哪份更新。v1.2 的处理方式：全量文件定为唯一真源，分叉的条目逐条对照知识库取更准确的版本，或者重写，子集再按 query_id 从全量重新生成。其中：
